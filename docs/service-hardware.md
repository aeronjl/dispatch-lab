# Recovery of service hardware

New configurations select `faults.hardware_model = actuator-interlock/1`. The plant adapter reports `plant-service-contracts/11`: hardware failures and their command/test observations apply whether recovery is enabled, disabled, or logistics is absent. `equipment_recovery_enabled` enables the separate `service-hardware/1` recovery workflow and its compatible capabilities and stocks. It does not determine whether equipment can fail.

Configurations saved before this distinction retain `recovery-gated/1` when loaded. That compatibility model preserves the original behaviour, including the defect that disabling equipment recovery also disabled service-hardware interlocks. Its output keeps the original adapter versions and does not acquire retrospective new-model evidence. Such charger-fault comparisons cannot rank recovery value. Existing results and publications are preserved; `field-support-v3.json` defines a new matched-physics study instead of rewriting them. The advanced setup shows which physical model is selected.

The reduced hardware model distinguishes a latched mobile control hold, an open mobile drive power stage, an open dock charger power stage and a portable pump power loss. These are illustrative prepared modules. A private scheduled fault activates on an integer plant boundary and persists until a compatible procedure changes it. The plant's transient process-fault setting does not clear a service-hardware fault. No arbitrary mechanical jam, robot navigation, electrical protection design or personnel injury is simulated.

An ideal actuator interlock rejects a command while the relevant hardware is unavailable. It consumes no motive energy in this open-circuit/held-command fixture. The rejected command is reported at the next plant boundary. It does not identify the cause. Portable pump failure does not prevent its service vehicle from travelling. Prepared function tests consume their separately configured electricity and observe encoder/load tracking; probe electronics are independent of the failed motive power stage. These are bounded ideal feedback channels, not a calibrated predictive-maintenance model.

The independent monitor consumes only eligible command and test readings. Before an informative command, hardware is **unobserved** and an initial attempt is permitted; this is not a healthy diagnosis. Failed feedback blocks subsequent reliance on the asset. No private cause or future onset enters this decision. A docked robot with a drive failure can still receive charging when its independent charger is operable. A stranded robot cannot receive an imaginary dock charge.

Under the independent model, the basic logistics drive test uses `supervised-drive-test/2`. It reports tracking only if its configured test outcome succeeds **and** the drive is physically operable at that interval. Retrieval changes location, never the failed module. The test emits both a return-to-work reading and a hardware-monitor reading from the same measured response. A failed test leaves the robot unavailable. Private response operands remain in retrospective receipts, separated from controller observations.

Remote help attempts one bounded control release, then a separate function test. A release can clear a control hold, but cannot replace a failed power stage. Finite remote hours, a shared operator, communications and a declared shift constrain every procedure. A successful test can permit a guided return using recorded stopping location, declared return time, battery energy and return reserve. A failed test or elapsed assistance wait leads to compatible human retrieval. Neither a release attempt nor a completed journey is itself proof of working hardware.

Returned hardware receives a function test. Persistent failure requires a typed compatible spare and a crew replacement procedure, followed by another test. An unsuccessful post-replacement test remains escalated. The replacement changes only the named hardware module; it cannot repair the electrolyser, a process sensor or another robot. Fault labels and hidden procedure success stay in retrospective execution records.

A portable operator can pack the stopped tool and return in the existing vehicle, subject to finite crew hours, route and shift availability. This is the same uninjured operator already present, not a second invisible callout. The procedure moves the tool without claiming repair. A function test and, where needed, a compatible pump-module replacement establish its subsequent usability. The original partial cleaning, consumed water/materials and failed work order remain recorded.

If guided return is interrupted, its newly reported stopping point becomes the retrieval target. The eventual physical return links all unrecovered interruptions of that same hardware. A previous control release cannot clear a fault injected at a later boundary. Each release and replacement is linked to its own post-work test; a later successful replacement cannot make the earlier failed release appear verified.

In this illustrative layout the service gate/apron appears at the diagram's lower right. Existing vehicle, operator, portable tool and dock illustrations show recorded procedures. A requested function test pulses the hardware indicator while its position remains unchanged, so the animation does not assert successful motion before test evidence arrives. A prepared probe supplies ideal encoder/load feedback; it does not simulate detailed test instrumentation or arbitrary remote inspection. During fractional playback, illustrations retain the existing convention of showing the current decision's planned phases until the next completed plant boundary; completed observations and quantities remain separately labelled.

Current crew, remote and electrical quantities use the shared resource ledger. Typed module consumption is recorded separately in the service cost model; unpriced modules remain unknown. Independent audit reconstructs fault lifecycles, test responses and timing, checks rejected commands, and rejects positive work with a failed actuator even if its failure receipt was omitted. These are numerical verification claims, not calibrated reliability or equipment certification. Scope-specific current tests are `tests/test_hardware_physics.py` and `tests/test_service_hardware.py`; older artifact results apply only to their saved implementation identities.
